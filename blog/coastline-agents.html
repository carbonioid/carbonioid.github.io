I'm currently doing a big project to do with procedural terrain generation. My end goal is to have a full generation pipeline that generates a coastline, heightmap, rivers, foliage and biomes. Those islands above were generated by my coastline algorithm.

What I describe here is a technique detailed in the paper Controlled Procedural Terrain Generation Using Software Agents. Their method generates remarkably good results for how simple it is, but I found the paper was missing some of the finer implementation details that I had to guess my way through.

That said, this post should hopefully fill in those missing details. I'll also discuss how to adapt the algorithm and its parameters to generate interesting coastlines. Finally, I'll talk about some mathematics I derived to have more intuitive control over how much land agents generate.

A larger landmass. More info on how to adapt landmass size later.

The Algorithm

Let's start with some terminology: we're generating a coastline on a discrete rectangular board where each pixel value is either land or sea. A coastline pixel is a land pixels that borders sea. All pixels on the board start as sea and the algorithm's purpose is to flip some pixels into being land. In the rest of the article, I'll refer to pixels as points.

This algorithm is based on coastline agents. These are objects with a position which teleport around the board creating land based on some criteria. The agent is assigned a fixed budget of tokens, and once it runs out of tokens (1 token is used for each time land is placed), it splits into two smaller agents each with half of its tokens. Agents keep subdividing like this until their children have too few tokens to continue.

An outline of the coastline agent's behaviour, from the original paper. This will make more sense once I've explained the whole algorithm.

An agent has the following properties attached to it:

  • Position: the initial position of the agent. This determines how attractors & repulsors are placed.
  • Coastline: all locations where the agent has placed land, plus its initial position
  • Token budget: the number of land squares the agent is allowed to place
  • Attractor & Repulsor points: points in different directions from where the agent starts. These determine how candidate land points are scored
  • Search direction: a random direction that the agent will search in if it can't find any candidate points. An easy way to implement this is to choose one of the four cardinal directions.

The purpose of some of these won't be evident yet; this list exists mostly as a reference of the rest of this section.

Scoring

The most important part of the algorithm is the criterion that agents create land based on. Each agent stores two points: an attractor and a repulsor. These points should be in different directions from one another, relative to where the agent starts. The agent aims to place land near the attractor, and far from the repulsor and the board's edges. At some point $p$, its score is given by $$d_r(p) - d_a(p) + 3d_e(p)$$where $d_{r}(p)$ is the squared distance from the repulsor, $d_{a}(p)$ is the squared distance to the attractor, and $d_{e}(p)$ is the squared distance to the nearest edge. We try to maximise this score, which means making $d_{a}(p)$ as small as possible.

Agent Loop

This is the loop of actions that runs for each agent that is currently alive (has >0 remaining tokens) on every iteration.

Each agents stores a coastline, which is a list of tiles it has previously placed land on (initially, this list just contains the agent's starting position.) On each iteration, the agent chooses a random coastline point and scores all the sea points that border it. The point with the highest score is made land and added to the agent's coastline. Staying in the local area of its coastline in this way helps agents produce distinct structures.

If for some reason there are no sea squares bordering any of the agent's coastline (this happens most often when the agent is first initialised and then other agents run), the agent moves in its stored search direction to find a land point that does border sea. Once that's found, the agent scores the neighbours of this point and places land in the same way as before. Optionally, you can add the land point that was found to the agent's coastline.

Agent Division

Once an agent runs out of tokens (more precisely, the number of land tiles placed equals their initial token budget) it is killed: it will no longer generate any coastline. Then either:

If its token budget is less than the token_limit (we'll explain the impacts of this later), then no children are created.

Otherwise, if its token budget $\geq$ token_limit, then it splits into two child agents, each with half the initial token budget of their parent. (you can take floor(budget/2) and ceil(budget/2) to ensure tokens are conserved, but it doesn't matter all that much.) Each child agent gets new attractor and repulsor points based on its position.

Since we never split agents with 1 token, the agent will always have a coastline of at least two points when splitting. The child agents' positions can either be randomly selected from the coastline, or you can try to prioritise squares that actually border sea and only use truly random points as a fallback. Either will work, but I opted for the latter.

Generating Repulsors & Attractors

As a small aside, "in different directions" is pretty up to interpretation. I've literally just made one generate anywhere in positive, positive (relative to the starting position of the agent) and the other in negative, negative. This works surprisingly well but I imagine some more advanced logic would be useful.

Running the Simulation

So, you've programmed all that behaviour. Now all that's left is to initialise some agents on your board and let them divide and generate land. For each agent you initialise, you should set the point it begins on as land so that it has a valid coastline.

Parameters

There are four parameters you can change to control how land is generated:

  • How many agents you initialise
  • The positions of these agents
  • The token budgets of these agents
  • The minimum token_limit for agent division

The first three are pretty intuitive: if you want large, continuous landmasses, create a few agents with large budgets. If you want many small islands and peninsulas (from agents' land happening to connect), create many agents with smaller budgets.

The token_limit is a bit less obvious: basically, you're cutting off how small the agent budgets can be. A lower token_limit will result in smoother terrain, whereas higher token_limit gives rougher terrain. However, higher token_limit can also make the coastline look noticeably artificial.

One last thing. You might've noticed I said that each agent generated the same amount of land, but increasing the token limit should make the same token budget generate less land. To confuse matters further, the amount of land created doesn't scale linearly with token budget. My new contribution to this algorithm is an analytic solution that links total land created to token budget and token_limit.

Converting area to tokens

If we initialise an agent with $t$ tokens and token_limit 1, it will generate $t$ land on its first iteration, and then about $t\log_{2}(t)$ land on all subsequent iterations (because $\log_{2}t$ is approximately the number of times you can halve $t$.) So, where $N$ is the amount of land created: $$ N = t(1+\log_{2}(t)) $$ If we then add in our token limit $S$, then the amount of land generated is approximately $$ t(1+\log_{2}(t)-\log_{2}(S)) $$ To be completely accurate, we would need to floor these algorithms, but that would make having a single equation as the solution very difficult. If we don't, we can do this: $$ \begin{align} t(1+\log_{2}(t)-\log_{2}(S)) & = N \\ t\left( \log_{2}\left( \frac{2t}{S} \right) \right) & =N \\ t\left( \ln \left( \frac{2t}{S} \right) \right) & =N\ln 2 \text{ by change of base} \\ \frac{2t}{S}\ln\left( \frac{2t}{S} \right) & = \frac{2N}{S} \ln 2 \\ \text{Let}\frac{2t}{S} &= e^y \\ e^y\ln e^y & = \frac{2N}{S}\ln 2 \\ ye^y & = \frac{2N}{S} \ln 2 \\ y & = W\left( \frac{2N}{S} \ln 2 \right) \\ \frac{2t}{S} & = \exp{\left(W\left( \frac{2N}{S} \ln 2\right)\right)} \text{ by substitution back in} \\ t & = \frac{S}{2}\exp{\left(W\left( \frac{2N}{S} \ln 2\right)\right)} \end{align} $$The function $W$ is the lambert W function, such that $W(we^w) = w$. It can be calculated in basically no time on a modern CPU. So when we want to create $N$ land with smoothing factor $S$ we use this many tokens: $$ t = \frac{S}{2}\exp{\left(W\left( \frac{2N}{S} \ln 2\right)\right)} $$ This isn't completely accurate but it's generally within about 1-10% which is acceptable for me. Also, it's interesting how this is actually linear in $S$.

Conclusion

All the code for this project is on a github repository, as well as some other algorithms. Also check out a really big image I made with this algorithm or a colored one (darker colors indicate agents with less tokens.)

Overall, I've been quite impressed with how realistic the images these agents generate are, given how simple the algorithm is. Agent-based generation is also a cool paradigm in general: if you want another feature on your map, you just need to write an agent that can generate it. Very extensible.

If you feel like coding this yourself or just playing with the program on the repo, feel free! Both are a fun time.
